# Code Review

Оценка кодовой базы по состоянию на текущую версию.  
Цель: зафиксировать сильные стороны, технический долг и приоритеты улучшений.

## Общая оценка

| Критерий | Оценка | Комментарий |
|----------|--------|-------------|
| Архитектура | **Хорошо** | Чёткое разделение API / pipeline / domain / UI |
| Читаемость | **Хорошо** | После рефакторинга frontend модульный; `App.css` всё ещё крупный |
| Надёжность | **Средне** | Нет тестов, sandbox небезопасен для production |
| Документация | **Онбординг в `docs/`** | Старт: [onboarding.md](onboarding.md). `DOCUMENTATION.md` в корне — только legacy Streamlit |
| Безопасность | **Низко для prod** | Нет auth, exec в sandbox, нет лимитов upload |

**Вердикт:** проект хорошо подходит как **локальный инструмент аналитика**. Для публичного деплоя нужен отдельный hardening-спринт.

## Сильные стороны

### Backend

1. **Python-first пайплайн** — детерминированные метрики и графики вместо ненадёжного LLM-кода.
2. **Инкрементальные `results`** — UI получает данные по мере готовности через SSE.
3. **Персистентность задач** — переживает рестарт uvicorn (`job_state.json`).
4. **Параллелизм** — `asyncio.to_thread` и `gather` без блокировки event loop.
5. **Экспорт** — качественные DOCX/XLSX с форматированием, on-demand для старых jobs.
6. **Модульность core** — `data_analysis`, `data_insights`, `visualization`, `reports` изолированы.

### Frontend

1. **Реактивный UX** — hero→dock анимация, степпер, вкладки с индикаторами данных.
2. **Модуль `results/`** — каждая вкладка в отдельном файле, `sectionMeta` централизует логику.
3. **Темы** — `data-theme` + `data-theme-mode`, расширяемо без дублирования селекторов.
4. **API-клиент** — единый `parseApiDetail`, blob-скачивание для DOCX.
5. **Форматированный просмотр** — `AnalysisView` / `ReportView` вместо сырого `<pre>`.

## Качество по модулям

### `pipeline.py` — **B+**

**Плюсы:** линейный поток, понятные `store.update`, параллельное сохранение.  
**Минусы:** функция ~200 строк; `_truncate` объявлена внутри шага; смешение оркестрации и I/O.

**Рекомендация:** вынести шаги в отдельные async-функции `async def step_structure(ctx)`.

### `data_analysis.py` / `data_insights.py` — **A-**

**Плюсы:** чистая доменная логика, без UI/HTTP.  
**Минусы:** нет unit-тестов на граничные случаи (пустые столбцы, один столбец).

### `llm.py` — **B**

**Плюсы:** кэш клиента, thread offload.  
**Минусы:** нет retry/timeout; падение Ollama валит весь шаг без graceful degradation.

### `jobs.py` — **B+**

**Плюсы:** SSE pub/sub, disk recovery.  
**Минусы:** глобальный singleton; нет TTL/очистки старых jobs.

### `routes.py` — **B**

**Плюсы:** whitelist файлов download, валидация graph_count.  
**Минусы:** вся логика в одном файле; нет rate limiting.

### Frontend `results/*` — **A-**

**Плюсы:** SRP, переиспользуемый `textFormat`, `CorrelationTable`.  
**Минусы:** `ResultsPanel` toolbar можно вынести в `ResultsToolbar.jsx`.

## Рекомендации по приоритету

### P0 — перед любым публичным деплоем

1. Аутентификация + привязка job к пользователю.
2. Лимит размера файла (например 50 MB).
3. Sandbox: отключить или изолировать (Docker, RestrictedPython).
4. HTTPS + закрытый Ollama.

### P1 — качество и поддержка

1. pytest: `analyze_data_structure`, `compute_metrics`, `parse_hypotheses`, `GET /health`.
2. Обновить `README.md` → ссылка на `docs/`.
3. Удалить legacy `parsers.py`, `code_runner.py`, неиспользуемые промпты.
4. Retry LLM (2 попытки, timeout 120s).

### P2 — UX и DX

1. Разбить `App.css`.
2. E2E smoke (Playwright): upload → дождаться completed.
3. Job cleanup cron (удаление jobs старше N дней).
4. OpenAPI examples в `models.py`.

## Заключение

Кодовая база **зрелая для локального продукта**: понятный пайплайн, хороший UX, осмысленный отказ от LLM-generated code в пользу Python. Главные пробелы — **тесты, безопасность sandbox и актуализация README**. Документация в `docs/` закрывает пробел «как это работает»; следующий шаг — автоматизировать проверки из чеклиста выше.
